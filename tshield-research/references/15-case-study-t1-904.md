## 2. 初步识别（5分钟快速分析）

### 2.1 文件类型识别

```bash
$ file T1_904_0414.sh
T1_904_0414.sh: ELF 64-bit LSB pie executable, ARM aarch64, version 1 (SYSV), dynamically linked, interpreter /system/bin/linker64, stripped
```

**发现**：
- 虽然扩展名是 `.sh`，但实际是 ELF 可执行文件
- ARM64 架构，Android 平台
- PIE 可执行文件
- stripped（无符号表）

### 2.2 Section 数量检查

```bash
$ readelf -S T1_904_0414.sh | grep -c "\["
4
```

**发现**：只有4个 section！

正常未加壳的 ARM64 ELF 通常有20+个 section。只有4个 section 是典型的加壳特征。

### 2.3 入口点反汇编

```bash
$ objdump -d --start-address=0x4be1920 --stop-address=0x4be1940 T1_904_0414.sh

0000000004be1920 <.text+0x1b09560>:
 4be1920:       f81f0fed        str     x13, [sp, #-16]!
 4be1924:       5285fd0d        mov     w13, #0x2fe8
 4be1928:       72b660cd        movk    w13, #0xb306, lsl #16
 4be192c:       f90007ed        str     x13, [sp, #8]
 4be1930:       17fe72a6        b       0x4b7e3c8
```

**发现**：入口点是一个 5 指令 Stub！

```armasm
str x13, [sp, #-16]!     ; 保存 x13
mov w13, #0x2fe8          ; 函数ID低16位
movk w13, #0xb306, lsl #16 ; 函数ID高16位 → 函数ID = 0xb3062fe8
str x13, [sp, #8]         ; 保存函数ID到栈
b #0x4b7e3c8               ; 跳转到统一解密器
```

这是 T盾 的典型 Stub 模式！

### 2.4 Program Headers 检查

```bash
$ readelf -l T1_904_0414.sh

  LOAD           0x0000000000000000 0x0000000000000000 0x0000000000000000
                 0x00000000000003c0 0x0000000000926ac0  R E    0x4000
```

**发现**：第一个 LOAD 段 filesz=0x3c0（960字节），memsz=0x926ac0（约9.4MB）！

filesz 远小于 memsz，这是加壳的典型特征——文件中只有壳代码，运行时解密原始代码到内存。

### 2.5 特征字符串搜索

```bash
$ strings -a T1_904_0414.sh | grep -i "T-Protector\|tshield\|T盾"
T-Protector T
```

**发现**：文件中包含 "T-Protector T" 字符串！

### 2.6 初步结论

满足以下所有 T盾 特征：
- ✅ Section 数量极少（4个）
- ✅ 入口点是 5 指令 Stub
- ✅ 所有 Stub 跳转到同一个统一解密器（0x4b7e3c8）
- ✅ 第一个 LOAD 段 filesz << memsz
- ✅ 文件中包含 "T-Protector" 字符串

**结论**：确认是 T盾 / T-Protector 加壳。

### 3.2 关键段分析

#### LOAD[2]：壳代码段

- 文件大小：0x3c0（960字节）
- 内存大小：0x926ac0（约9.4MB）
- 权限：RE（可读可执行）
- 内容：ELF头 + Program Headers + 第一阶段壳代码
- 特点：文件极小，内存极大，运行时由壳代码填充

#### LOAD[5]：解密后代码段

- 文件大小：0（文件中无内容）
- 内存大小：0x1afb638（约27.6MB）
- 权限：RE（可读可执行）
- 内容：运行时由统一解密器填充解密后的函数代码
- **这是动态 dump 的最关键段！**

#### LOAD[6]：加密 payload 段

- 文件大小：0x2c93c40（约46.6MB）
- 内存大小：0x2c93c40（约46.6MB）
- 权限：RE（可读可执行）
- 内容：所有函数的 Stub + 统一解密器 + 加密的函数代码体 + 映射表
- 熵：7.98 bits/byte（高熵，加密数据）

## 4. Stub 模式分析

### 4.1 入口点 Stub（0x4be1920）


**函数ID = 0xb3062fe8**

### 4.2 PREINIT 函数 Stub（0x4be5a68）

```armasm
0x4be5a6c: mov w13, #0x643e           ; 函数ID低16位
```

### 4.3 Stub 模式总结

| 项目 | 入口点 Stub | PREINIT Stub |
|------|-------------|--------------|
| 虚拟地址 | 0x4be1920 | 0x4be5a68 |
| 函数ID | 0xb3062fe8 | 0x730c643e |
| 统一解密器 | 0x4b7e3c8 | 0x4b7e3c8 |

| 大小 | 20字节 | 20字节 |

**关键发现**：
1. 所有 Stub 的指令模式完全相同，只有函数ID不同
2. 所有 Stub 都跳转到同一个统一解密器地址（0x4b7e3c8）
3. 函数ID是32位立即数，由 mov+movk 构造
4. 函数ID保存在栈上（sp+8位置），统一解密器从栈上读取

### 5.3 OLLVM 混淆分析

前40条指令中，约30条是混淆指令：

| 混淆指令 | 出现次数 | 说明 |
|----------|----------|------|
| ror（循环右移） | 3次 | 无意义的循环移位 |
| orr（按位或） | 3次 | 包括 orr x,x,x（无操作） |
| neg（取负） | 2次 | 连续两次取负恢复原值 |
| orn（或非） | 4次 | 无意义的或非操作 |
| ubfx（位域提取） | 3次 | 无意义的位域提取 |
| rev（字节序反转） | 4次 | 连续两次反转恢复原值 |
| eor（异或） | 2次 | 包括 eor x,x,x（结果为0） |
| eon（异或非） | 2次 | 无意义的异或非 |
| mvn（取反） | 1次 | 无意义的取反 |
| asr（算术右移） | 1次 | 无意义的右移 |
| bic（位清除） | 1次 | 无意义的位清除 |
| lsl（逻辑左移） | 1次 | 无意义的左移 |
| sxtw（符号扩展） | 1次 | 无意义的符号扩展 |

**混淆比例**：约75%的指令是无意义的混淆指令！

### 5.4 关键发现

1. **统一解密器被 OLLVM 指令替换混淆**：大量无意义的 ror/orn/eon/rev/ubfx 指令
2. **保存了约20个寄存器**：stp x7,x11 / stp x30,x29 / stp x25,x2 / ...
3. **关键调用**：在 0x4b7e478 处调用 `bl #0x5a90278`，这很可能是真正的解密函数
4. **混淆常量**：开头对 0x1ab135ae 做各种混淆运算，可能是在计算密钥或索引

## 7. 脱壳方向建议

### 7.1 推荐方法：动态内存 dump

**理由**：
- 不需要逆向复杂的 OLLVM 混淆解密器
- 技术成熟，成功率高
- 只要能运行程序，就能 dump

**步骤**：
1. 在 Android 模拟器/真机上运行程序
2. 触发所有功能（让所有函数被解密）
3. dump LOAD[5]（解密后代码段，0x15dc3c0-0x30d8000）
4. dump LOAD[6]（payload段，包含Stub和明文部分）
5. 修复 ELF 结构
6. 验证

### 7.2 备选方法：Frida hook 统一解密器（需授权注入）

**理由**：
- 可以拦截每个函数的解密过程
- 可以建立函数ID → 解密后地址的映射
- 可以批量收集所有解密后的函数

**步骤**：
1. 定位统一解密器地址（0x4b7e3c8）
2. 编写 Frida 脚本 hook 解密器
3. 拦截每个函数的解密，记录函数ID和解密后地址
4. 触发所有功能，收集所有解密函数
5. dump 所有解密后的函数
6. 重建 ELF 文件

### 7.3 高难度方法：静态逆向解密器

**理由**：
- 不需要运行环境
- 可以完全理解解密算法

**难点**：
- 解密器被 OLLVM 混淆，75%指令是无意义的
- 需要逆向映射表结构
- 需要复现解密算法
- 工作量大

**步骤**：
1. 用符号执行工具（angr/miasm）去混淆
2. 逆向统一解密器，理解解密逻辑
3. 定位函数ID → 加密代码映射表
4. 复现解密算法
5. 写脚本批量解密所有函数
6. 替换 Stub 为真实函数
7. 修复 ELF 结构

## 9. 总结

### 9.1 样本特征

| 特征 | 值 |
|------|-----|
| 加壳类型 | T盾 / T-Protector |
| 架构 | ARM64 |
| 核心机制 | 函数级加密 + Stub分发 + 统一解密器 |
| 混淆 | OLLVM 指令替换（解密器） |
| 统一解密器 | 0x4b7e3c8 |
| 解密后代码段 | 0x15dc3c0 - 0x30d8000（约27.6MB） |
| 加密payload段 | 0x30d83c0 - 0x5d6c000（约46.6MB，熵7.98） |

### 9.2 推荐脱壳方法

**动态内存 dump**（推荐）→ 触发所有功能 → dump LOAD[5] → 修复 ELF → 验证

### 9.3 关键难点

1. **函数级加密**：需要触发所有功能，让所有函数被解密
2. **OLLVM混淆**：解密器被混淆，静态逆向难度大
3. **ELF修复**：dump 后需要修复 ELF 结构才能正常分析
4. **反调试**：可能有反调试检测，需要绕过
